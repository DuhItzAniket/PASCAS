# 2. PRIMARY ENGINEERING PRINCIPLE

The mathematical engine must be **Pascal-first**.

Do NOT build the core functionality by secretly relying on:

- Python
- SymPy
- MATLAB
- Mathematica
- Wolfram Alpha
- JavaScript mathematical libraries
- remote APIs
- an online CAS

The project may optionally integrate external systems in a future experimental/integration layer, but the actual core scientific engine must be implemented in Pascal.

The system must remain useful without internet access.

---

Use a layered architecture.

The conceptual architecture must be:

```text
                         PascalMath Studio
                                |
                +---------------+---------------+
                |                               |

                |                               |
       Lazarus / LCL UI              HTML/CSS + Pascal

              2D                              3D
             Graphs                           Graphs
```

The most important design principle is:

**Shared mathematical core + separate platform adapters.**

# 4. DESKTOP TECHNOLOGY

Baseline technology:

- Free Pascal / Object Pascal
- Lazarus
- LCL
- Native desktop controls where appropriate
- BGRABitmap or equivalent Pascal-compatible rendering technology when beneficial
- OpenGL only where necessary for advanced 3D

Do not introduce Qt, Electron, .NET, Python or Java merely to simplify implementation.

Prefer native Pascal solutions.

The agent must inspect the installed toolchain first rather than blindly assuming versions.

Current baseline may be FPC 3.2.2 + Lazarus 4.8, but verify the local environment and adapt carefully.

---

# 5. WEB TECHNOLOGY

The website must preserve the Pascal-first principle.

Use:

- Pascal mathematical core
- Pas2JS for browser-compatible Pascal code
- HTML
- CSS
- Browser DOM APIs
- Canvas/SVG/Web APIs as appropriate
- JavaScript only as a thin interoperability layer where required by browser APIs or Pas2JS
- Web Workers where useful
- WebAssembly only if a technically justified Pascal-compatible route becomes stable and maintainable

Do not turn the entire application into a JavaScript application with a tiny Pascal component just to satisfy the requirement.

The mathematical engine remains Pascal.

The web application should preferably operate as:

```text
Browser
   |
HTML/CSS shell
   |
Pascal UI/controller compiled using Pas2JS
   |
Shared Pascal mathematical engine
   |
Graph / CAS / calculator
```

If some shared Pascal component cannot compile under Pas2JS because it relies on desktop-only APIs, refactor the architecture so platform dependencies remain outside the shared core.

The core must therefore remain as platform-neutral as reasonably possible.

# 10. COMPUTER ALGEBRA SYSTEM

Build the CAS incrementally.

### Simplification

```text

x * 0 = 0
x - x = 0
x^1 = x

cos(0) = 1
ln(1) = 0
```

### Expansion

```text

→ a² + 2ab + b²
```

### Factorization

```text
x² + 2x + 1

→ (x+1)²
```

### Differentiation

```text
d/dx x² = 2x
```

```text
d/dx sin(x) = cos(x)
```

```text
d/dx f(x)g(x)
```

Use product, quotient and chain rules.

### Integration

Start with numerical integration.

Then implement increasing symbolic integration capabilities.

### Limits

Eventually:

```text
lim(x→0) sin(x)/x = 1
```

### Equation solving

Support numerical solving first.

Then symbolic polynomial solving.

Then increasingly general equations.

# 22. SECURITY

NEVER implement arbitrary expression execution with something equivalent to:

```text
eval(userInput)
```

Do not allow user mathematical expressions to execute arbitrary system code.

The expression parser must be a controlled language.

Validate:

- Input length
- Recursion depth
- Number of operations
- Memory usage
- Matrix dimensions
- Graph sampling limits
- Iteration limits
- Numerical runaway conditions

Avoid denial-of-service behavior caused by pathological expressions.

For web deployment, never expose unsafe JavaScript evaluation mechanisms.

# 26. PERFORMANCE

The application must remain responsive.

Important rules:

- Do not block the GUI thread unnecessarily.
- Use background workers/threads for expensive operations.
- Use cancellation tokens/flags for long computations.
- Avoid recalculating unchanged expressions.
- Cache ASTs.
- Cache compiled evaluation forms where useful.
- Cache graph samples when viewport has not changed.
- Limit pathological graph sampling.
- Use adaptive sampling instead of simply calculating millions of points.
- Profile before optimizing.

For browser execution, use Web Workers where appropriate.

# 45. MATHEMATICAL CORRECTNESS RULE

Never implement an algebraic simplification without considering domain restrictions.

For example, transformations involving:

```text
sqrt
log
division
complex values
powers
absolute values
```

can require conditions.

The CAS must not blindly apply transformations that change mathematical meaning.

Where domain assumptions are required, represent them explicitly or document the supported assumptions.

---

# 46. GRAPHING CORRECTNESS RULE

Never blindly connect every sampled point.

Handle:

```text
NaN
Infinity
large jumps
discontinuities
domain errors
```

Example:

```text
tan(x)
```

must not display an artificial diagonal line across the asymptote.

Adaptive sampling should be introduced progressively.

---

# 47. UI CORRECTNESS RULE

Never make the UI responsible for mathematical calculations that belong to the core.

Bad:

```text
ButtonOnClick()
    calculate derivative manually
```

Good:

```text
ButtonOnClick()
    CoreEngine.Differentiate(...)
```

The UI is a client of the mathematical engine.
